02The problem

The screen is not an API.

Desktop applications expose pixels, not structured intent. A model can decide what to do, but it cannot act until it can see the interface, locate the right control, and verify what changed.

01

Perceive

High-resolution screenshots, mixed DPI, small icons, and text at different scales.

02

Ground

Map a natural-language instruction to a target coordinate on the screen.

03

Act, then verify

Click or type, then check whether the visible state actually changed.

Most benchmarks stop at grounding. This project treats grounding as a measurable component, not the whole claim.

Intelligent Systems · CV

Can it see the target?

Measure grounding accuracy on high-resolution Windows screenshots. Break results down by application, element type, and interface condition.

Methods: detection, OCR, visual grounding, robustness.

Data Mining · DM

Why does it miss?

Analyze the labeled grounding records. Find co-occurring failure conditions and fit an interpretable model that generalizes across applications.

Methods: association rules, CART, grouped validation.

One combined paper. The contributions remain distinguishable by their questions, methods, and results; the run records are shared.
05Evaluation data

ScreenSpot-Pro,
narrowed to Windows.

A high-resolution GUI grounding benchmark: 1,581 examples across 23 professional applications and three operating systems. The Windows subset contains 1,020 examples, matching the framework's target platform.

What it gives

Instruction, screenshot, and ground-truth target box. Icon and text targets, including buttons, menu items, and controls.

Why it fits

Professional interfaces, small targets, high resolution. A hard test of grounding rather than an easy toy set.

What it does not give

No browser tasks, no action sequences, no state transitions. Static screenshots only.

License: MIT. The dataset card and the project repository declare MIT. The screenshots depict proprietary applications, so the dataset license does not grant rights to the applications themselves. The full benchmark spans Windows, macOS, and Linux; this study uses the Windows subset.
06Research questions

Two questions.

The first asks whether the perception layer works. The second asks what its failures mean.

RQ1

Grounding

How accurately can a model-agnostic, vision-only pipeline ground natural-language instructions to GUI targets on high-resolution Windows screenshots, and how does accuracy vary by application, element type, and interface condition?

RQ2

Failure analysis

Which visual and interface conditions co-occur with grounding failure, and can a shallow CART decision tree describe those conditions and generalize across unseen applications?

07Method

One row per request.

Each grounding request becomes a record: instruction, screenshot, target box, predicted point, model, application, element type, and outcome. Labels are correct, mislocalized, not found, or ambiguous.

Primary metric

Point-in-box accuracy on the Windows subset. Secondary: distance to target, per-application accuracy, per-element-type accuracy.

Validation

Grouped cross-validation by application. Report per-application results, not only the pooled average.

Records

JSONL source of truth → DuckDB query and feature assembly → Parquet derived tables. Arrow only as an in-memory handoff.

Sample target

At least 500 labeled requests and 100 observed failures before fitting models. A planning heuristic, not a formal power calculation.

No random row splits. No leakage from ground-truth target geometry into predictive features.
08Primary algorithm

A tree that
explains the miss.

CART is the primary analysis model because it produces readable rules, not just a score.

Interpretable

Each root-to-leaf path is a conjunction of conditions that leads to a success or failure.

Mixed features

Numeric and categorical predictors without manual pre-binning.

Interactions

Small predicted target × icon type × low OCR confidence.

Controlled

Depth 3–5, cost-complexity pruning, grouped validation.

Descriptive paths, predictive test. Grouped validation checks whether the learned conditions generalize; features must be available before the ground-truth box is consulted.
09Supporting analyses

The tree is primary.
The rest triangulate.

Association rules

Descriptive co-occurrence. Report support, confidence, and lift for conditions such as small target + icon + low OCR confidence. Not a second predictor.

Random forest

Accuracy benchmark and feature importance. Check whether the same features dominate under an ensemble. Not per-request rules.

Logistic regression

Linear baseline. Test whether the tree's non-linear interactions actually buy predictive performance.

Clustering

Exploratory profiles. Describe failure subgroups and check whether tree leaves align with natural clusters. Not predictive.

One main algorithm, clearly labeled supporting analyses. No ensemble is presented as the primary model.
10Scope

Be precise
about the claim.

Will claim

  • A model-agnostic, vision-only grounding pipeline.
  • Measured accuracy on the Windows subset of ScreenSpot-Pro.
  • Interpretable failure conditions with grouped validation.
  • A reproducible record schema for later work.

Will not claim

  • Full autonomous computer use.
  • Live Windows control or end-to-end task success.
  • Browser coverage from ScreenSpot-Pro.
  • Causal effects or generalization beyond the benchmark.
Known risks. Screenshot rights remain with application vendors · no browser tasks · static screenshots do not test capture or DPI · single-tree instability · small sample · ground-truth leakage if post-hoc features enter the predictor.
